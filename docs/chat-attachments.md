# 聊天文本附件

聊天窗口的“添加文本文件”可选择、展开预览、移除和发送附件；也可只发送附件而不输入消息。

- 支持 UTF-8 的 `.txt`、`.md`、`.markdown`、`.csv`、`.json`、`.log`。每条消息最多 5 个，每个最多 32 KiB，合计最多 64 KiB。空文件、无效 UTF-8、二进制控制字符和不支持的扩展名会明确报错，不截断正文。
- 图片、PDF、Office、压缩包暂不支持。现有 provider 的 `image` 能力用于生成/编辑图片，不表示模型能读取图片。本功能只使用已经声明 `text` 能力的模型。
- 文件在浏览器本地读取、预览，发送时才随经过认证和 CSRF 校验的聊天 POST 上传。服务端重新校验名称、正文和 UTF-8 字节数，不信任客户端大小、MIME 或 URL；不调用公开媒体上传接口、不创建附件文章或公开链接，也不抓取外部 URL。
- 完整正文以 JSON 编码的文本参考数据加入用户消息，实际发送给当前 AI 服务商。所有 provider 继续接收既有的字符串 `content`，不依赖原生文件/视觉 API，也不需要流解析 PR #963 / plugins#20。
- 文件名、字节数、正文保存在所属消息的 JSON payload 中，沿用当前会话所有权检查。历史恢复、后续对话、模型切换及重试均重新组装完整正文；删除会话会删除这些消息和附件。无需数据库迁移或独立文件清理。
- 为避免附件内容或引用它的回复被复制到管理员可见的 AI 审计记录，包含附件历史的生成调用使用 `recordContent: false`：不记录请求/响应正文或 HTTP 参数，仅保留身份、模型、状态和用量等元数据。普通聊天的既有审计策略不变。插件和外部服务商仍能看到实际发送的内容，遵循其各自的数据策略。
- 服务端确认消息已保存（开始 SSE）后清空待发附件；发送被拒绝时保留输入和附件。网络结果不确定时应刷新会话核对，避免重复发送。模型生成失败后，已保存附件仍可通过原有“重试回复”使用。切换会话清空未发送附件，不跨会话携带。

所有历史仍受现有 400000 字符的上下文上限约束，超限会终止生成，不能保证各模型具有相同的 token 窗口。附件文本是不可信参考数据，不提升工具权限或跳过写操作确认；本功能并不保证消除模型提示注入。
